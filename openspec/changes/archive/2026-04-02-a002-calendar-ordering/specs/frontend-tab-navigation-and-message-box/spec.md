## MODIFIED Requirements

### Requirement: 員工可在三個主 TAB 間切換，且我的訂單只聚焦訂單內容
系統 SHALL 讓員工在「訂便當」「我的訂單」「修改密碼」三個 TAB 間切換。其中「訂便當」TAB MUST 以月行事曆作為主要互動區，顯示本月訂餐狀態、日期格互動與訂餐管理視窗；「我的訂單」TAB MUST 顯示目前員工的訂單清單、取消按鈕狀態與取消流程，並維持既有 MessageBox 規則。系統 MUST 不再要求員工透過訂餐日期下拉作為主要訂餐入口。

#### Scenario: 員工切換到我的訂單
- **WHEN** 員工在登入後點擊「我的訂單」TAB
- **THEN** 系統在不重新整理整頁的情況下顯示個人訂單清單與可取消狀態

#### Scenario: 員工在我的訂單 TAB 取消訂單
- **WHEN** 員工在「我的訂單」TAB 點擊取消
- **THEN** 系統先顯示確認 MessageBox，確認後才送出取消請求

#### Scenario: 員工在訂便當 TAB 看到月行事曆
- **WHEN** 員工切換到「訂便當」TAB
- **THEN** 系統在單頁狀態中顯示本月訂餐行事曆，而不是以日期下拉作為主要互動

### Requirement: 員工訂便當頁的日期互動與管理操作必須透過視窗與確認提示呈現
系統 SHALL 在員工於「訂便當」TAB 點擊日期格時，以視窗承接訂餐與管理操作。點擊空白可訂日期時，系統 MUST 顯示當天可選便當清單；點擊已有訂單日期時，系統 MUST 顯示已訂便當資訊及「修改」「取消」入口。執行修改或取消前，系統 MUST 透過既有 MessageBox 顯示確認提示，經確認後才送出對應 API 請求。

#### Scenario: 點擊空白日期後顯示便當選項視窗
- **WHEN** 員工在「訂便當」TAB 點擊一個空白可訂日期
- **THEN** 系統開啟視窗，列出當天可選便當清單並允許送出訂餐

#### Scenario: 點擊已訂日期後顯示管理視窗
- **WHEN** 員工在「訂便當」TAB 點擊一個已有訂單的日期
- **THEN** 系統開啟視窗，顯示已訂便當資訊與修改、取消入口

#### Scenario: 修改或取消前顯示確認提示
- **WHEN** 員工在日期管理視窗中點擊修改或取消
- **THEN** 系統先顯示確認 MessageBox，確認後才執行對應操作
