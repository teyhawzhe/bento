## Context

最新版 `../uml/input/A002.md` 將員工訂餐主流程從「選日期、選便當、送出」提升為「以月行事曆瀏覽整月訂餐狀態，點日期格開啟訂餐或管理視窗」。目前系統已有兩塊可重用能力，但尚未被組成新版 A002 所需體驗：

- A002 既有後端已提供 `GET /api/orders/menu`、`POST /api/orders`、`PATCH /api/orders/{id}`、`DELETE /api/orders/{id}`、`GET /api/orders/me` 與截止規則服務。
- A014 已提供管理員 `work_calendar` 查詢/編輯能力與前端月曆 cell 呈現邏輯，但目前僅限管理員使用，且 API 路徑為 `/api/admin/calendar`。

因此這次設計的核心不是重寫 A002 業務規則，而是把 A014 的工作日資料與 A002 的訂單/菜單資料在員工端整合成單一月行事曆互動模型，同時移除目前不再符合需求的下拉式主流程。

## Goals / Non-Goals

**Goals:**
- 提供員工端 `GET /api/calendar`，讓「訂便當」TAB 可以載入指定年月的上班日資料。
- 以月行事曆取代現有日期下拉，讓員工直接在日期格上看見非上班日、空白可訂日與已訂日期。
- 重用既有 A002 訂單建立/修改/取消規則與 A014 `work_calendar` 資料，避免新增第二套日期判斷模型。
- 在員工端互動中保留既有 MessageBox 確認流程與截止規則提示。

**Non-Goals:**
- 不改動 A014 管理員行事曆設定流程或其資料模型。
- 不改寫 A002 的星期五 12:00 新增/修改截止與前一日 16:30 取消截止規則。
- 不在本次引入新的前端路由系統或拆分大型 `App.tsx` 架構。
- 不更動管理員端菜單管理、供應商管理與訂單管理的既有行為。

## Decisions

### 1. 新增員工端 `GET /api/calendar`，直接重用 A014 `work_calendar` 資料
- 理由：新版 A002 已明確把員工行事曆列為獨立 API 路徑。沿用既有 `work_calendar` 資料可以讓「可互動日期」與 A014 / A015 維持同一套真相來源，避免員工端再自行推算平日/假日。
- 替代方案：讓員工端直接呼叫 `/api/admin/calendar` 或在前端用星期幾推算。未採用，前者權限語意錯誤，後者會與人工調整過的上班日脫節。

### 2. 保留 `GET /api/orders/menu` 的資料視窗規則，但補上 `supplier_name`
- 理由：員工行事曆視窗仍需要當日可選便當清單，而既有 `GET /api/orders/menu` 已承擔「只回傳 A002 可訂視窗內有效菜單」的規則。新版 A002 只新增顯示格式需求，因此延用原端點並補足 `supplier_name` 最小變更即可。
- 替代方案：為行事曆彈窗新增一條 `GET /api/orders/menu-by-date`。未採用，因為會把日期視窗與菜單篩選規則拆成兩套 API。

### 3. 員工訂餐頁以「月行事曆 + 操作視窗」取代下拉式主流程
- 理由：新版 A002 已將行事曆視圖定義為主互動模型，繼續保留雙下拉作為並存主流程會讓規格與 UI 入口雙軌化。行事曆格可以同時承接狀態瀏覽與操作入口，更符合需求文件中的使用流程。
- 替代方案：保留下拉表單，額外在旁邊顯示行事曆。未採用，因為會保留舊流程並增加狀態同步複雜度。

### 4. 日期格狀態以「工作日 + 當月訂單 + 可訂菜單」三層資料合成
- 理由：單靠工作日資料只能判斷能不能互動，單靠訂單資料只能判斷是否已訂，還需要 `GET /api/orders/menu` 告訴前端哪些日期在當前視窗內實際有可選菜單。前端以這三層資料合成 cell state，可以明確區分非上班日、不可訂工作日、可訂空白日、已訂日。
- 替代方案：全部狀態由後端一次回傳。未採用，因為會引入新的聚合 DTO 與更重的後端耦合，本次可先沿用既有資料源在前端組裝。

### 5. 修改與取消前仍沿用既有 MessageBox，訂餐內容選擇使用專屬操作視窗
- 理由：MessageBox 已適合確認類互動，但不適合承載菜單清單選擇。將「選便當」與「看已訂資訊」放在專屬視窗，將「確定修改/取消」留給 MessageBox，可延用現有確認模式並減少視覺跳躍。
- 替代方案：全部互動都塞進 MessageBox。未採用，因為會讓選單內容與確認文案混在同一個元件，互動過於侷促。

## Risks / Trade-offs

- [員工端新增月行事曆後，`App.tsx` 狀態量與條件分支會進一步上升] → 優先抽出行事曆狀態計算 helper，避免把 cell 判斷散落在 JSX 中。
- [以三份資料在前端合成日期格狀態，容易出現某月資料不同步] → 載入員工頁時固定一起刷新 calendar、menus、orders，並在訂餐/改單/取消成功後統一重載。
- [A002 新增 `GET /api/calendar` 會與 A014 的 `/api/admin/calendar` 形成平行端點] → 在設計與 spec 中清楚切分員工唯讀查詢與管理員維護用途，避免未來權限混淆。
- [移除下拉主流程可能讓部分既有測試或使用者習慣失效] → tasks 需同步更新前端互動測試與說明文案，並將下拉流程視為被替代而不是保留備援。

## Migration Plan

- 先新增 OpenSpec delta specs，固定員工端行事曆 API、行事曆狀態與前端互動模型。
- 後端在既有 A002 路徑中補上員工 `GET /api/calendar`，並擴充員工菜單 DTO 的 `supplier_name`。
- 前端把「訂便當」TAB 重構為月行事曆 + 操作視窗，移除日期下拉主流程。
- 補上 controller/service/frontend 驗證，確認截止規則、非上班日不可互動、已訂日期管理與取消按鈕顯示都符合新版 A002。

## Open Questions

- `GET /api/calendar` 是否需要限制只能查詢當月、下月等有限範圍，或先接受任意有效年月：A002 只說供員工端行事曆使用，未明確限制。
- 行事曆日期格在「上班日但不在 A002 可訂視窗內」時，應呈現 disabled 樣式還是一般空白但不可點擊：這需要 UI 文案與樣式定義一起決定。
- 已訂日期若其訂單已超過取消截止但仍在本月行事曆中，管理視窗是否保留只讀資訊與不可操作提示：規格已隱含取消按鈕需隱藏，但畫面語意可再細化。
